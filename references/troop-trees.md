# 兵种替换、升级图与战斗数值

## 新建与替换

先从当前游戏 XML 查实际 ID；显示名不是标识。普通线与贵族线分别检查，不能从类似名称猜入口。Native v1.4.8 本机帝国例证：普通新兵 `imperial_recruit`，最低级贵族新兵 `imperial_vigla_recruit`；其他版本或兵种覆盖模组应重新核实。

同 ID 替换适合已有招募入口继续使用新外观；新增 ID 可避免直接覆盖原兵种，但需要接入招募、文化、模板或升级入口。用户只要求换模型时保留文化、等级、技能、武器和升级图，除非它们与目标模型装备方案冲突或用户另有要求。

XML 数据可能按 ID 或子节点合并。参考工程采用 XSLT 精确替换目标 NPCCharacter 整节点，并保留其余节点，避免原版防具 roster 合并回来。不要把这种做法当成不检查加载顺序的万能覆盖；同目标的其他模组可以再次覆盖它。

替换方案至少验证：

- 对当前原始 NPCCharacters 实际应用转换，目标存在且只改变指定 ID。
- 无关兵种节点与原始内容一致；新增方案单独检查新增节点与目标入口。
- 兵种 race、性别、年龄、Monster、技能和装备引用有效；检查所有 roster、平民装备及装备集合。
- SubModule.xml 的入口/加载顺序与实际模块一致，资源名与已安装包能对上。

不要把只可解析 XML 当成游戏已采用新兵种；需要查看招募/百科及实际出生角色，诊断可记录 Character.Race、装备和所用动作。

## 升级图

升级目标指向 NPCCharacter ID。原版兵种升级到自定义种族、或自定义种族升级回原版种族，可以通过不同目标 NPCCharacter 实现；种族并非整条升级线必须不变。不是把现有战场 Agent 的模型直接变身，装备、性别与 race 来自升级后的角色定义。

用有向图检查目标解析、重复边、自环、意外环、入口可达性及终点。常规兵种树要无环；用户明确需要特殊循环时再设计相应玩法。检查分支数、角色定位及升级成本/坐骑要求的本机机制，不能只画图而不核实引用。

Level 到 Tier 的映射应查当前 CharacterObject 与战役模型，不凭空添加一个不被 schema 读取的 tier 属性。参考新兵 Level=6/T1 仅是本机案例。调武器、弓箭或坐骑时还要检查弹药与角色分类，避免外观任务意外改变步兵、远程、骑兵和骑射身份。

最低级新兵换种族而升级目标仍为原版时，升级后会使用原版模型。用户要整棵自定义树才扩展后续节点；要求两套模型用于不同入口时，不自动改全部升级单位。

## 模型、防具与固有属性

外观不产生护甲值：完整身体中直接包含衣服、盔甲形状，也不等于穿了相应 Item。无防具的种族应单独核对生命、技能、装备护甲和伤害计算，不能凭网格材质推断战斗属性。

用户要求严格无装备但有种族固有护甲时，不虚构 skins.xml 的护甲属性，不用隐藏装备代替。对本机 v1.4.8，按 [RaceTroopBuilder 的种族默认护甲接入约定](race-troop-builder.md#种族默认护甲接入约定) 使用默认数据和运行组件，兵种替换器可继承或覆盖。其他版本先核对实际护甲更新与伤害接口；不要顺带调整全局 Native 平衡。

## 自动战斗与实际战斗

查当前版本实际使用的 MilitaryPowerModel 和 CombatSimulationModel，以及是否被其他模组替换。自动模拟不是实际武器碰撞、动画、身体尺寸与装备减伤的逐帧复现，不能直接假设新增场景护甲会提高自动战斗战力。

本机 Native v1.4.8.119303 的只读 DLL 核对例证：普通兵 `DefaultMilitaryPowerModel.GetDefaultTroopPower` 为：

```text
(2 + Tier) × (10 + Tier) × 0.02
```

T1 的基础值为 0.66，英雄另有逻辑。领队、环境、地形、攻守、步兵/远程/骑兵类别等继续影响后续计算。装备可间接改变类别；这个基础公式不直接累加护甲和武器伤害。例证来源为参考工程 `reports/autoresolve_analysis.md` 的版本、DLL 哈希与回读记录，不作跨版本保证。

仅换种族外观且 Tier/类别不变时，通常沿用原版自动战斗，不必人为填一个战力常数。只有用户希望新增防御/能力也影响模拟时，才单独设计修正并核对实际战斗与自动战斗，防止双重加成。
