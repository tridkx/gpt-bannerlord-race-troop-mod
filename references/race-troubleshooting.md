# 种族故障与回归

## 从可用版本隔离改动

记录本次反馈对应版本与时间，核对实际安装包哈希。从最后一次用户确认可用的包/标签，比较生成脚本、身体组成、skin 槽、动作集、绑定矩阵、材质和新增形变。若回归始于“加手势”等任务，先检查它移走或替换了什么，不先假定贴图、比例或布料是根因。

必要时恢复已验证显示路径，保留独立源文件/实验资源，在最小验证中一次测试一个新机制。回退带来的功能损失要明确说明；“恢复手显示”不等于“手指弯曲实现了”。用户已接受的比例与非目标部位应保持可比较。

## 启动或角色生成崩溃

对齐同次日志、事件和崩溃转储的版本/时间与异常位置。读取装备技能的崩溃参考获取工具方法；不要仅凭“最近加了种族/布料”就推断原生崩溃原因。

本机 Native v1.4.8 的已验证易错点：

| 触发 | 表现与处理 |
| --- | --- |
| 删除 `hair_meshes` 容器或其 `group_id` | 参考案例启动阶段失败；当前 Native 容器属性与顺序需保留 |
| 将发型/胡须列表完全清空 | 参考案例城镇招募等角色生成阶段失败；保留原版零号无发型/无胡须描述 |
| 皮肤、骨架、Monster、动作集引用缺失 | 检查实际加载入口与目标性别/年龄皮肤；不能仅看 NPC 的 race 字符串 |

零号项是原版描述，不是自行给一个叫“none”的 mesh。参考工程直接深拷贝原版无 name 的首项，包括其内部标签；不要伪造未知 schema 的占位 XML。未来版本需要重新对照 Native。

## 地图明暗频闪与动作集缺口

画面区域忽明忽暗与地图小人反复消失是不同症状。先核对动态动作集名称与错误日志，注册机制见[场景动作集](race-registration.md#动作集批量注册与场景覆盖)。缺失 map／poses 是注册缺口，不足以认定为画面明暗频闪根因。按固定地点、镜头、时间做单变量对照：仅隐藏目标地图图标，再单独检查动态图影、材质、LOD 和反复置脏／重建；保留人物真实 Race 与属性。UI 预览修复跳过地图，不能把 tableau 的强制重建循环推广到地图 AgentVisuals。

## 主角读档种族与装备外观

本机 v1.4.8 的英雄加载经 `InitializeHeroBasicCharacterOnAfterLoad` 执行 `Race = originCharacter.Race`；运行时更改种族而原始模板仍是 human 时可能读档重置。XML 模板本身为自定义种族的英雄不能一概判断会重置。用户要求主角持久化时，用 CampaignBehavior.SyncData 保存稳定英雄标识与种族名称，加载后先恢复再采集；不只存会随模块顺序变化的整数索引，也不在 Tick 中持续强制赋值。旧档没有记录时不能推断原种族，同进程换档需清理会话缓存。参考[公开持久化实现](https://github.com/haterade22/TAOM/blob/bannerlord-1.4.5/Main/Features/HeroRace/RacePersistenceService.cs)，调用时序仍以当前游戏代码验证。存档列表的 BasicCharacterTableau 头像与实际加载 Hero.Race 分别检查。

用户要求装备隐形但保留属性时，可评估有效不可见 CosmeticItem：原 Item／ItemModifier 提供护甲和重量，外观物品提供网格及部分身体遮盖。null 会回退原装备外观，不能表示隐藏；本机 CosmeticItem 没有直接保存标记，需要换装、读档及人物重建时重新应用。BodyMeshType、BodyDeformType 等仍有读取原装备的路径，须同时保护完整身体、头发和手部。优先作用于目标人物的渲染／生成副本，不改共享 ItemObject。地图、UI 与战场各自验证，不能把材质透明或删除实际装备当作完整实现。此项只在用户请求时实现，不因动作集注册任务自动新增。

## 朝向与身高

先确定反馈来自战斗同地面、招募预览还是百科，检查源前向与最终顶点/骨架方向。多次旋转必须相对当前交付结果，不能在脚本中重复叠加。脸和身体方向应分开观察，不能凭脸朝后就只旋转头骨。

低身高应分解为源单位、模型尺寸、绑定骨架尺寸、skin 缩放与运行时 AgentScale；全局变换、脚/头骨高度和原版成人参照比预览包围盒更可靠。用户口语“还没到腿”不等于已测得的米数。无法用当前缩放解释差距时保留不确定性，不把它写成比例错误的定论。

### skin 参数生效与源体型校准

`skins.xml` 的 `min_scale` 是有效的整体缩放参数，但 `min_scale=1.0` 不保证最终 `GetScale()`／`AgentScale` 为 1.0。本机 Native v1.4.8 的人物预览在未显式传入缩放时，通过 `MBBodyProperties.GetScaleFromKey(race, gender, bodyProperties)` 调用原生引擎计算倍率；不能只看 XML 数值判断游戏尺寸。

固定外观种族应分别记录源模型单位与尺寸、skin 参数和实际运行倍率，不复用其他模型的身高或校准值。源比例保留和游戏有效尺寸校准是两项检查。若源尺寸正确而游戏整体偏小，优先校准整体缩放，不拉长四肢或改脸、胸腰形体补偿。UI 适配应保留已有缩放，避免帧矩阵与 Scale 重复相乘。

需要确认参数是否生效时，在用户授权下发布明显倍率的临时测试，保留旧交付包，保持 TPAC、模型、骨架、权重和 DLL 不变，只修改任务种族 skin 缩放及版本号；重启游戏后比较同一性别、年龄、身体参数及场景。参数响应经实测确认后，可用 `新参数 = 旧参数 × 目标实际倍率 / 实测实际倍率` 作整体校准。用户要求“源体型”时，目标是在已确认单位的源模型上获得约 1.0 的最终倍率，不是机械地把 `min_scale` 改回 1.0。人物预览和战场分别验收，男性记录不自动证明女性、不同身体键或年龄分支一致。

本机天香 T5 PVE 例证（2026-10-12）：`min_scale=1.0` 的男性创建界面实测倍率为 `0.9031746`；参数改为 `2.0` 后日志记录 `1.80634916`，用户确认生效。按该人物参数恢复源尺寸可估算 `min_scale≈1.1072056`，该校准值只适用于对应基线，不能作为新种族默认值。恢复后的实际尺寸仍需用户复测；两倍参数生效不代表所有界面、战场和体型分支均已验收。

## 静态手臂内收与绑定方向

**触发与表现**：完整角色按源模型改了肩、肘、腕位置，但 rest 旋转仍全部沿用 human；创建页面或持武器站立时，上臂/前臂异常靠近身体，运动时表现可能不同。区分骨架绑定方向偏差、蒙皮权重串到躯干、实际动作本来就背手，不先用换动作或外移网格掩盖问题。

1. 从最终 TPAC 回读世界/局部 rest 矩阵，比较肩→肘、肘→腕的实际方向与父骨的纵向轴。当前 human 上臂/前臂骨段主要沿局部 X；其他骨架按实际矩阵核对。骨段长度正确并不代表方向正确；局部平移出现额外 Y/Z 偏移需要检查源姿势差异，但不能把所有侧向偏移都判错。
2. 对齐必要的上臂、前臂和中间扭转骨的绑定方向，按模型保持滚转连续。可用把原纵向轴转向源骨段的最短旋转作为起点；重新计算局部矩阵及逆绑定。保留源网格、关节支点、骨骼语义与层级，不默认旋转整条骨架或改角色比例。
3. 检查共享肩/腕边界及量化权重。补查创建页面实际动画、空手、单手/双手武器站立、持弓、挥刀、骑乘；只检查物品栏待机或最大边长比不能证明没有穿模。动画片段与骨骼动画通过 GUID 核对，不能仅按相似名称匹配。

本机第一套纫秋少女 v0.1.3（2026-10-12）：上臂绑定方向偏差约 18.8°、前臂约 6.8°。修正方向并保留源形状、支点与权重后，用户确认手臂内收问题修好。这些角度是该模型证据，不是通用修复参数。物品栏背手属于另一个待机动作问题，不能据此推断也已修复。

## 手腕与手指是两项机制

手腕扭曲先检查支点、手掌/前臂末端的关系、扭转骨混合权重和法线，抽样握持、挥刀、持弓。普通蒙皮没有给每根手指独立活动并不一定是漏骨：本机 human 的原版手势主要是形变通道，Native hands_female_a 有 26 个通道，实际权重不使用 finger0。

[官方动画文档](https://moddocs.bannerlord.com/asset-management/asset-types/animations/)说明 left_hand_pose/right_hand_pose 驱动手部形变。这证明机制存在，不能证明任意手部网格写入 26 帧就接入成功。

### WuduRaceTest 验证边界（2026-10-10）

- v0.2.0 完整身体含双手：用户确认模型可用与高度到原版成人胸口，手指不弯、手腕稍扭。
- v0.2.1 将双手从身体移出、注册独立 hands_mesh 并添加形变：手部不可见。
- v0.2.2 开启 uses_stitching、v0.2.3 对齐基础编辑坐标 W=1：用户仍报告双手不可见。不得把这两项写成已解决的根因或独立手部必需规则。
- v0.2.4 恢复双手到完整身体、停用运行时形变，保留手腕优化：用户确认手可见、手腕更好看。源文件保留实验形变；手指动态弯曲尚未实现。

这是已验证的恢复方案，不是“自定义种族不支持手势”的结论。新模型可继续尝试独立手部，但必须在原有手可见的最小基线上单独验证，再推广到完整包。

### 不可见时区分四层证据

1. **资源包**：最终 TPAC 中是否确有手部和各级 LOD、有效面数、权重与材质；是否因拆分从身体移除了手却没有实际替代显示路径。
2. **透明与材质**：解码最终贴图检查 Alpha，检查 UV 所采区域、透明混合/裁切、顶点 Alpha 和运行时颜色。不要只看原 PNG；布料 Alpha 也不要一律填 255。
3. **人物注册**：目标 skin 的 hands_mesh/身体引用、装备 SkinMask、性别/年龄选择及动作集。资源 `MetaMesh.GetCopy` 成功不等于它挂到了人物。
4. **最终场景**：人物实际部件、面数、材质、LOD、形变/GPU 状态与蒙皮位置。合批名称不能直接代表原始手部名；手原始资源有面但场景没显示，还需查实际挂载与渲染。

本次失败版的证据：最终 body_D 解码 Alpha 全为 255，材质不透明，原始手部资源读到 1472 面且 HandsVisible 开启，仍不可见。因此透明贴图不是本次解释；独立手部路径的具体引擎原因尚未证实。

## 诊断应服务于区分假设

用当前版本可用接口记录目标兵种 race、性别/年龄、Monster、AgentScale、装备与 SkinMask；需要时记录原始资源面数、场景网格面数、颜色、包围盒和骨骼位置。日志限定目标和数量，避免大量输出；写日志失败不应影响游戏。

诊断 DLL 默认只读，不为观察现象偷偷添加或替换人物网格。若确需代码改变渲染路径，应将其作为明确的实现变更，分别测试招募/百科预览和实际战斗；只在 Mission 中添加网格不保证 UI 一致。

报告区分：结构/回读通过、离线动画预览、用户实机确认与仍待确认。已确认失败的方案不再写成“效果待首次复测”，长期说明以当前可用路径为准；带日期的历史报告可保留当时结论。
